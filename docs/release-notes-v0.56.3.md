# git-ctx v0.56.3

이번 릴리스는 `explain-search-result` 가 호출마다 **15초씩 멈추던** 자기 잠금을 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

- `explain-search-result` 는 청크 커서를 **열어 둔 채로** 검색 설정을 다시 조회하고 있었습니다. SQLite 는 연결을 하나만 쓰도록 열려 있어(단일 라이터 보호), 이 두 번째 질의는 자기 자신이 쥐고 있는 연결을 기다립니다. 문장 타임아웃이 끝나야 풀리므로 호출마다 15초가 걸렸고, 그 사이 설정 읽기는 실패해 **검색 모드 설명이 기본값으로 대체**되고 있었습니다. 실측 15,005ms → 3~14ms.
- 커서를 열기 전에 설정을 읽도록 순서를 바꿨습니다. PostgreSQL 은 연결 풀이 여러 개라 이 증상이 드러나지 않았습니다.

## 같은 유형 정리

같은 패턴이 어디에 더 있는지 코드 전체를 훑었습니다. 지금 실제로 멈추는 곳은 위 한 곳뿐이었고, 나머지는 커서를 다 읽은 뒤 호출하기 때문에 `database/sql` 이 연결을 이미 돌려준 상태였습니다 — 다만 루프에 `break` 하나만 생기면 똑같이 15초로 돌아갑니다.

- **벡터 동기화가 커서를 쥔 채 벡터 DB로 배치를 보내고 있었습니다.** 자기 잠금은 아니지만(다른 풀), 저장소 전체를 동기화하는 동안 SQLite 의 단 하나뿐인 연결을 네트워크 왕복마다 붙잡아 **다른 모든 요청을 막습니다.** 이제 한 페이지(500건)를 읽고 커서를 닫은 뒤 전송하며, 청크 id 로 이어서 읽습니다.
- OpenSearch projection 은 `_bulk?refresh=wait_for` 응답을 기다리는 동안 커서를 쥐고 있었습니다. 지금은 먼저 닫습니다.
- `query-docs` 후보 조회, `find-file` 의 원격 목록 보강, 의존성 사용처 조회, MCP 호출 CSV 내보내기도 다음 데이터베이스 호출 전에 커서를 명시적으로 닫습니다.

## 검증

- 단일 연결 저장소에서 5초 안에 끝나지 않으면 실패하는 회귀 시험(순서를 되돌려 실패하는 것까지 확인)
- 커서를 쥔 채 데이터베이스를 다시 호출하는 지점을 코드 전체에서 조사(102개 질의 지점)
- 실제 20만 청크 인스턴스에서 32개 도구 전체 스윕: 이 도구를 제외한 모든 호출이 335ms 이하였고, 수정 후 이 도구도 3~14ms
- FTS5 빌드·태그 없는 빌드 양쪽 전체 단위·통합·race 테스트

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- `explain-search-result` 가 보고하는 검색 모드가 이제 실제 설정을 반영합니다. 이전에는 기본값이 표시됐을 수 있습니다.
