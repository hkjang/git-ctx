# git-ctx v0.76.1

이번 릴리스는 **v0.76.0에서 추가한 거절 카운터가 대량 탐색에 비례해 서버 CPU를 태우던 문제**를 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### 감사 줄 한 줄을 남기려고 서버 시간을 내주고 있었습니다

- v0.76.0의 카운터는 주소마다 **시도 시각을 전부** 들고 있었습니다. 그래서 **탐색의 비용이 탐색의 크기에 비례해 커졌습니다.**
- 실측: 한 주소에서 5만 번 거절 → **잠금을 잡은 채 3.4초**. 주소를 흩어 50만 번 → **18.6초**.
- 유휴 주소를 버리는 정리도 **거절마다** 돌았습니다. 맵이 가득 찬 뒤에는 매 요청이 추적 중인 주소 전부를 훑었습니다.
- 결과적으로 **인증되지 않은 호출자가 틀리기만 반복해도 서버 시간을 쓸 수 있었습니다.** 감사 줄 하나를 얻자고 치르기에는 나쁜 거래이고, 애초에 그 감사 줄이 목적이었습니다.

### 고친 방식

- 상태를 시도 시각 목록이 아니라 **횟수와 창 시작 시각**으로 바꿨습니다.
- 정리는 **시간으로 상각**합니다. 창보다 빨리 만료되는 것은 없으므로, 창의 일부가 지나기 전에 다시 훑을 이유가 없습니다.
- 같은 측정이 **27밀리초**와 **66밀리초**가 됐습니다.

### 메모리도 공격자 규모가 아니라 설치가 정한 값에 묶습니다

- 주소는 **4,096개까지 개별로** 셉니다.
- 그보다 넓게 퍼진 탐색은 **버리지 않고 하나의 항목으로 합쳐** 셉니다 — 그렇게 넓게 퍼진 탐색이야말로 가장 보고할 값어치가 있는 사건이고, 그것을 보고하는 데 공격자의 규모에 비례하는 메모리가 들면 안 됩니다.
- 합쳐 센 경우 감사 줄에 `countedUnder`가 함께 남습니다. **어떤 횟수도 조용히 남의 것이 되지 않습니다.**

## 검증

- 50만 번 거절을 한 주소에서, 그리고 흩어진 주소에서 각각 돌려 비용 상한을 확인 — 이 시험이 배제하려는 구현은 상한을 두 자릿수 배수로 넘깁니다
- 카운터가 들고 있는 주소 수가 정해진 경계를 넘지 않는지 확인
- 경계 직전까지는 개별로 세고, 그 뒤 첫 주소가 합쳐진 항목으로 들어가며 그 첫 거절이 보고되는지 확인
- 창이 지나면 횟수가 다시 1부터 시작하는지 확인
- 상각을 되돌리면 `many_addresses`가 16.7초로 실패합니다
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험, 릴리스 데이터베이스 업그레이드 시험, 콘솔 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- 감사 줄의 내용은 v0.76.0과 같되, 주소가 개별로 세어지지 않은 경우 `countedUnder`가 추가됩니다.
- **v0.76.0을 배포했다면 이 릴리스로 올리는 것을 권합니다.** 공개된 엔드포인트에서 인증되지 않은 요청만으로 CPU를 소모시킬 수 있습니다.
