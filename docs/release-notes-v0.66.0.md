# git-ctx v0.66.0

이번 릴리스는 **데이터베이스 연결 문자열이 바뀌면 플랫폼이 기동을 거부하고 모든 API 키가 인증에 실패하던 문제**를 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### 암호화 키가 DSN 문자열에서 파생되고 있었습니다

- 설정 암호화 키와 API 키 pepper 를 `sha256(연결 문자열)` 로 매 기동마다 다시 계산했습니다. 즉 **어디에도 저장되어 있지 않았습니다.**
- 온프레미스 설치는 보안과 무관한 이유로 연결 문자열을 바꿉니다 — 데이터 디렉터리 이동, 상대 경로를 절대 경로로, 질의 매개변수 두 개의 순서 교체, PostgreSQL 호스트 이름 변경.
- 그 중 무엇이든 하면 **키가 달라집니다.** 플랫폼은 자기 설정을 복호화하지 못해 기동을 거부하며 `cipher: message authentication failed` 를 냅니다 — 원인이 아니라 알고리즘 이름입니다.
- 동시에 **모든 API 키가 조용히 인증에 실패합니다.** pepper 도 같은 문자열에서 나오기 때문입니다. 에이전트 접근이 통째로 끊기는데 로그에는 권한 오류만 남습니다.
- 이제 키를 데이터베이스에 적어 두고 `GIT_CTX_RECOVERY_KEY` 에서 파생한 키로 감쌉니다. 복구 키는 이미 필수이고, 안정적이어야 하며, 운영자가 지키도록 되어 있는 유일한 비밀입니다.
- 이미 데이터가 있는 설치는 **DSN 이 만들어 낸 바로 그 값**이 그대로 기록됩니다. 재암호화가 없고, **어떤 API 키도 무효가 되지 않습니다** — 같은 비밀이 바뀔 수 있는 문자열에 의존하기를 그만둘 뿐입니다.
- 복구 키와 원래 연결 문자열을 **둘 다** 잃은 경우만 복구가 불가능하며, 그때는 무엇을 해야 하는지 운영자의 말로 설명합니다.

## 검증

- **실제 릴리스 바이너리가 쓴 데이터베이스를 현재 트리로 여는 시험**을 새로 추가했습니다(`test/store/upgrade.test.sh`). 기존 업그레이드 시험은 손으로 만든 "legacy 스키마" — 마이그레이션을 쓴 사람이 상상한 과거 — 만 다뤘습니다.
- v0.1.0(마이그레이션 9개)부터 현재까지 모든 릴리스에서 데이터가 살아남고, 읽히고, 쓸 수 있으며, **서버가 그 데이터베이스로 기동해 응답**하는 것을 확인했습니다. CI 에서 매번 돕니다.
- 마이그레이션 전수 점검: `ADD COLUMN NOT NULL` 에 DEFAULT 가 빠진 곳도, 컬럼 삭제·이름 변경도 없습니다.
- DSN 매개변수 순서만 바꿔 기동하고 설정을 읽고 **기존 API 키로 MCP 호출이 되는지**, 복구 불가능한 경우가 알고리즘 이름 대신 원인을 말하는지 회귀 시험. 수정을 되돌리면 정확히 `cipher: message authentication failed` 로 실패합니다.
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험

## 업그레이드 참고

- 마이그레이션 `048_platform_keys.sql` 이 추가됩니다. 자동 적용됩니다.
- **첫 기동은 반드시 기존 `GIT_CTX_DB_DSN` 으로** 하십시오. 그때 키가 데이터베이스에 기록되며, 이후로는 연결 문자열을 자유롭게 바꿀 수 있습니다.
- `GIT_CTX_RECOVERY_KEY` 는 이제 설정 암호화의 뿌리이기도 합니다. 백업하십시오.
- 재암호화나 재색인은 없습니다. API 키는 그대로 동작합니다.
