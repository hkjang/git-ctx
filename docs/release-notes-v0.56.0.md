# git-ctx v0.56.0

이번 릴리스는 색인된 내용 검색에 **전문 검색 인덱스**를 넣습니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 개선

- 지금까지 색인 내용 검색은 청크를 **전부 훑어서** 일치를 찾았습니다. 저장소 400개·청크 20만 개로 재보니, 아무 데도 없는 단어를 찾는 데도 전체 스캔 비용이 들었습니다. 카탈로그가 열 배 커지면 초 단위가 됩니다. 찾을 대상을 조회할 곳이 없었기 때문입니다.
- 이제 SQLite FTS5 인덱스를 만들어 **일치하는 행만 읽습니다.** 인덱스는 트리거로 청크 테이블을 따라가고, 인덱스가 없는 데이터베이스(FTS5 없이 빌드된 바이너리, PostgreSQL)에서는 예전처럼 훑어서 답합니다 — 가속기가 없다고 기동을 막지 않습니다.
- **단어 안쪽 일치는 그대로 유지됩니다.** 인덱스는 단어와 접두사만 알기 때문에 `invoice` 로 `settleInvoice` 를 찾지 못합니다. 그래서 인덱스 조회가 답을 채우지 못하면 기존 훑기로 보충합니다. 회수율은 그대로 두고 속도만 얻습니다.
- `get-platform-status` 가 이 인스턴스의 검색이 어느 경로를 쓰는지 보고합니다.

## 실측 (저장소 400 · 청크 200,000)

```text
질의                         이전      이후
없는 단어(kubernetes)        267ms    191ms   (인덱스 조회 후 보충 훑기)
흔한 단어(payment)            53ms     47ms
두 단어(settlement retry)     53ms     61ms
부분어(ettle)                  -       51ms   (회수율 유지 확인)
```

- 흔한 단어의 결과가 나온 저장소 수: 8개 → 13~17개. 읽은 행이 전부 실제 일치이므로 상한에 걸려도 표본이 덜 치우칩니다.
- 인덱스가 답을 채우는 질의(대부분의 식별자 검색)는 보충 훑기 없이 한 자릿수 ms 로 끝납니다.

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다. 인덱스는 기동할 때 만들어지고, 기존 청크는 그때 한 번 채워집니다. 큰 데이터베이스에서는 첫 기동이 그만큼 길어집니다.
- 소스에서 직접 빌드한다면 `-tags sqlite_fts5` 를 주어야 인덱스가 생깁니다. 태그 없이 빌드해도 동작하며, 검색은 예전 훑기 경로를 씁니다. 공식 이미지와 릴리스 빌드에는 태그가 들어 있습니다.
- PostgreSQL 은 이번 릴리스에서 훑기 경로를 유지합니다. tsvector 인덱스는 별도 마이그레이션으로 검증해 넣습니다.

## 검증

- FTS5 빌드와 태그 없는 빌드 **양쪽에서** 전체 단위·통합·race 테스트
- 인덱스가 청크 테이블의 삽입·수정·삭제를 따라가는지, 인덱스 없는 데이터베이스를 열면 채워지는지 시험
- 두 경로가 같은 내용을 찾는지(정확 일치·접두사·경로 조각·단어 안쪽) 시험
- 실제 인스턴스에서 20만 청크 대상 지연·저장소 분포 실측
- 오프라인 이미지 빌드로 태그가 적용된 전체 시험 통과 확인
