# git-ctx v0.64.0

이번 릴리스는 **`read-file` 이 파일이 아닌 것을 파일이라고 내놓던 문제**를 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### read-file 이 파일의 일부만 돌려주면서 전체라고 말했습니다

- 저장된 청크는 **검색 색인이지 파일 사본이 아닙니다.** 청크 생성기는 코드에서 심볼 하나당 청크 하나를 만듭니다 — 그래서 `package` 선언, 임포트, 심볼 밖의 주석은 **저장되지 않습니다.** 마크다운은 제목 줄을 별도 컬럼으로 들어 올리고 빈 줄을 버립니다.
- 다시 읽어 이어 붙이면 5줄짜리 Go 파일이 1줄로, 12줄짜리 README 가 3줄로 나왔습니다. 그리고 `read-file` 은 그것을 **"lines 1-3 of 3"** 이라며 파일로 내놓았습니다.
- 그 파일을 읽고 편집하라는 지시를 받은 에이전트는 대부분을 지웠을 것입니다.
- 이제 **소스에 먼저 묻습니다.** 파일이 실제로 있는 곳은 거기뿐입니다.
- 소스에 닿지 못하면 색인이 여전히 답합니다 — 온프레미스 플랫폼은 장애 중에도 답해야 합니다 — 다만 **그것이 파일이 아님을 밝힙니다.** 무엇이 빠졌는지, 줄 번호가 재조립된 텍스트의 것이지 파일의 것이 아님을, 소스에 왜 닿지 못했는지까지.

### 색인되지 않은 파일에 대한 안내가 동작하지 않는 도구를 가리켰습니다

- `find-file` 은 색인되지 않은 파일에 대해 "search-code 나 소스 UI 를 쓰라"고 했습니다. `search-code` 는 색인된 내용을 검색하므로 **바로 그 파일에 대해 답할 수 없는 유일한 도구**입니다. 정작 읽어 내는 도구인 `read-file` 은 언급되지 않았습니다.

### 읽기 실패가 이유를 삼켰습니다

- 라이브 읽기가 실패하면 플랫폼은 이유를 알고 있었습니다 — 소스 미설정, 어댑터 기동 실패, 연결 거부 — 그 이유를 진단에 담아 놓고는, 호출자에게는 "읽을 수 없었다"고만 했습니다.
- 이제 그 이유가 답에 실립니다. 파일이 ref 목록에는 있으나 내용이 색인된 적 없다는 사실도 함께 — "저장소에 없는 파일"과 "색인된 적 없는데 지금 소스가 닿지 않는 파일"은 다릅니다.

## 검증

- 마크다운·Go·평문 파일을 색인한 뒤 `read-file` 결과를 원본과 대조하는 조사로 시작했습니다. 평문만 정확했습니다.
- 파일 전체가 돌아오는지(`TestReadFileReturnsTheWholeFile`), 소스 장애 시 색인 대체가 자기가 무엇인지 밝히는지(`TestTheIndexFallbackSaysItIsNotTheWholeFile`), 안내가 읽어 내는 도구를 가리키는지, 실패가 이유를 말하는지 회귀 시험. 수정을 되돌리면 12건이 걸립니다.
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- `read-file` 은 이제 호출당 소스 API 를 한 번 부릅니다. MCP 도구 캐시가 앞에 있고, 소스가 닿지 않으면 이전처럼 색인이 답합니다.
- 색인에서 답이 나온 경우 답의 성격이 바뀝니다 — 이전에도 부분이었지만, 이제 그렇다고 말합니다.
