# git-ctx v0.67.0

이번 릴리스는 **백업을 다른 기기에 복원할 수 없던 문제**를 고칩니다. 백업이 존재하는 이유가 바로 그 경우입니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### 백업을 만든 설치에서만 복원할 수 있었습니다

세 가지가 동시에 막고 있었습니다.

- **찾지 못했습니다.** 백업 목록은 자기 데이터베이스의 `backup_records` 를 읽습니다. 새 설치의 그 표는 비어 있으므로, 백업 파일이 디렉터리에 그대로 있는데도 목록은 `null` 이었습니다.
- **복원하지 못했습니다.** id 로 복원을 요청하면 `sql: no rows in result set` — 복구 한가운데의 운영자에게 데이터베이스 오류가 그대로 전달됐습니다.
- **열지 못했습니다.** 아카이브는 그 설치의 마스터 키로 봉인됐는데, 그 키는 **방금 잃어버린 데이터베이스의 연결 문자열에서** 파생된 것이었습니다.

고친 내용:

- 백업 목록이 디렉터리도 읽습니다. 어떤 행도 설명하지 않는 파일은 `discovered` 로 함께 나열됩니다.
- 기록이 없어도 파일 이름으로 복원합니다. 파일이 곧 백업이고, 아카이브 자체의 인증 암호화가 크기·해시 검사보다 강한 확인입니다.
- 새 아카이브는 **`GIT_CTX_RECOVERY_KEY` 에서 파생한 키**로 봉인합니다. 같은 복구 키를 가진 어떤 설치도 열 수 있습니다. 이전 아카이브는 설치 키로 계속 열립니다.

### 복원이 끝나도 설정을 읽지 못했습니다

- 복원은 키 자료를 포함해 데이터베이스 전체를 교체하는데, 실행 중인 프로세스는 기동 시 결정한 키를 계속 쓰고 있었습니다.
- 그래서 복원이 성공한 직후 **멀쩡한 데이터베이스에 대해 `Unable to decrypt setting`** 이 나왔습니다.
- 이제 복원 직후 키를 다시 읽습니다. 요청 게이트가 잠겨 있고 배경 작업이 멈춘 시점이라 아무것도 그 키를 쓰고 있지 않습니다.

## 검증

- 원본 설치에서 설정과 API 키를 만들고 백업을 받은 뒤, **빈 데이터베이스의 새 설치**에서 목록·복원·설정 읽기·그 API 키로 MCP 호출까지 하는 시험을 추가했습니다. 수정을 되돌리면 목록이 `null` 인 채로 실패합니다.
- 설치 키로 봉인된 구버전 아카이브가 그대로 복원되는지, 자기 키가 다른 설치에서 복구 키만으로 복원되는지 각각 시험
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험, 릴리스 바이너리 업그레이드 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- 이 버전부터 새 백업은 복구 키로 봉인됩니다. **`GIT_CTX_RECOVERY_KEY` 를 백업과 함께, 그러나 같은 곳이 아닌 데 보관하십시오** — 그것이 없으면 이제 아카이브를 열 수 없습니다.
- 이전 버전이 만든 아카이브는 그것을 만든 설치에서 계속 복원됩니다.
