# git-ctx v0.68.0

이번 릴리스는 **릴리스 이미지를 실제로 기동시켜 응답을 받아 보는 검증**을 추가하고, 이미지에서 아무도 읽지 않는 콘솔 사본을 들어냅니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 개선

### 릴리스 검증이 이미지를 띄워 보지 않았습니다

- 오프라인 이미지 검증은 아카이브 체크섬, `docker load`, 아키텍처, OCI 라벨, 실행 사용자, 그리고 `git-ctx -version` 한 줄을 확인했습니다.
- **서버를 기동시켜 본 적은 없습니다.** 빌드는 되는데 뜨지 않는 이미지는 고객에게 도달하는 릴리스 실패의 전형입니다 — 누락된 파일, 쓸 수 없는 데이터 디렉터리, 포트 바인딩, 기동 중 마이그레이션 실패는 `-version` 이 잡지 못합니다.
- 이제 **배포 매니페스트가 선언한 조건 그대로** 컨테이너를 띄웁니다 — 읽기 전용 루트 파일시스템, 모든 capability 제거, 권한 상승 금지, 비루트 사용자, 쓰기 가능한 곳은 `/tmp` 와 백업 볼륨뿐. 그 상태에서 `/readyz`, 공개 상태 엔드포인트, 콘솔 `/` 와 `/app.js` 가 모두 응답해야 통과합니다.
- 매니페스트는 지금까지 `kustomize build` 로 **렌더링만** 검증됐습니다. 이제 그 보안 설정에서 실제로 도는 것까지 확인합니다.

### 이미지가 콘솔의 두 번째 사본을 담고 있었습니다

- 콘솔은 바이너리에 내장되어 있습니다. `web/embed.go` 의 주석이 그 이유를 적어 두었습니다 — "체크아웃된 옛 web 디렉터리가 바이너리보다 낡은 화면을 서빙한다"는 문제를 없애기 위해서입니다.
- 그런데 Dockerfile 이 `web/` 를 `/var/lib/git-ctx/web` 으로 복사해, 없애려던 그 아티팩트를 이미지 안에 다시 만들고 있었습니다. 432KB 의 사본이 아무에게도 읽히지 않은 채 컨테이너 작업 디렉터리에 놓여 있었고, Go 소스(`embed.go`)까지 런타임 이미지에 실려 있었습니다.
- 복사를 들어냈습니다. 콘솔은 그대로 서빙됩니다.

## 검증

- 새 스모크 검사가 **기동하지 못하는 이미지를 실제로 거부하는지** 확인했습니다(진입점이 응답하지 않는 이미지로 exit=1).
- 콘솔 자산을 지운 이미지가 여전히 서빙된다는 사실로 내장 여부를 확인하고, 그 결과 Dockerfile 의 복사가 불필요함을 확인했습니다.
- 복사를 들어낸 이미지가 검증기를 통과하고 콘솔이 정상 서빙되는지 확인
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험, 릴리스 바이너리 업그레이드 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- `GIT_CTX_WEB_DIR` 로 콘솔을 디스크에서 서빙하던 경우, 이미지 안의 `/var/lib/git-ctx/web` 은 더 이상 없습니다. 그 용도는 UI 를 재빌드 없이 편집하기 위한 개발용이며, 직접 마운트한 디렉터리를 가리키면 됩니다.

## 오프라인 Docker 이미지

릴리스 자산은 아키텍처 접미사가 없는 다음 두 파일입니다.

- `git-ctx-v0.68.0.tar.gz`
- `git-ctx-v0.68.0.tar.gz.sha256`

```bash
sha256sum -c git-ctx-v0.68.0.tar.gz.sha256
gzip -dc git-ctx-v0.68.0.tar.gz | docker load
docker image inspect git-ctx:v0.68.0 --format '{{.Os}}/{{.Architecture}} {{.Config.User}}'
```

기대 결과는 `linux/amd64 10001`입니다. 아카이브에는 `git-ctx:v0.68.0`과 `git-ctx:0.68.0` 태그가 포함됩니다.

**전체 변경 내역**: https://github.com/hkjang/git-ctx/compare/v0.67.1...v0.68.0
