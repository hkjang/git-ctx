# git-ctx v0.75.0

이번 릴리스는 **URL에 박힌 자격증명이 마스킹되지 않고 색인·응답에 그대로 나가던 문제**를 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

> **업그레이드 시 전체 재색인이 한 번 일어납니다.** 아래 "업그레이드 참고"를 먼저 읽으세요.

## 보안 수정

### URL 자격증명 마스킹이 DB 스킴 3개만 알고 있었습니다

- 규칙이 `postgres`·`mysql`·`mariadb` 세 스킴만 지목했습니다. 그래서 **URL 자격증명이 마치 DB 문제인 것처럼** 다뤄졌습니다. 아닙니다.
- 이 플랫폼이 색인하는 저장소에서 자격증명이 나타나는 **가장 흔한 형태**는 토큰이 박힌 clone URL입니다. README, CI 설정, 셋업 문서에 그대로 있습니다.

  ```
  git clone https://x-token-auth:ATBB...@bitbucket.company/scm/kcb/app.git
  ```

  이 줄은 **아무 처리 없이** 색인에 들어가고 스니펫으로 다시 나왔습니다.
- 이제 스킴을 가리지 않습니다. `https://`, `mongodb://`, `redis://`, `sqlserver://`, `amqp://`, `ldap://` — 전부 해당합니다.
- **호스트는 남깁니다.** "어느 시스템의 자격증명인가"가 조치의 출발점이고, 그것까지 가리면 위험한 절반과 함께 쓸모 있는 절반을 버리게 됩니다.
- 비밀번호 쪽은 `@`를 허용합니다. `P@ssw0rd`는 사람들이 실제로 쓰는 비밀번호이고, 첫 `@`에서 멈추면 `ssw0rd`가 응답에 남았습니다.

### 사내 설치에서 실제로 나오는 다섯 형태가 원문 그대로 나갔습니다

규칙을 쓰기 전에 각각을 실제 sanitizer에 넣어 **원문이 그대로 돌아오는 것을 확인**했습니다.

| 형태 | 예 |
|---|---|
| Oracle thin 서술자 (구분자가 슬래시) | `jdbc:oracle:thin:scott/tiger@//db.company:1521/orcl` |
| Spring XML 속성 쌍 | `<property name="password" value="Sup3rSecret" />` |
| XML 엘리먼트 | `<password>Sup3rSecret</password>` |
| Authorization 헤더 | `Authorization: Bearer abcdefghijklmnop1234` |
| `curl -u`, `.netrc` | `curl -u admin:Passw0rd ...`, `machine host login svc-ci password s3cr3tvalue` |

- 어느 것도 대입문이 아니어서 기존 규칙이 닿지 않았고, 어느 것도 벤더 접두사나 엔트로피 하한에 걸리지 않았습니다.

### 규칙을 개선해도 이미 저장된 청크는 그대로였습니다

- 저장된 청크는 **색인 당시의 규칙으로만** 가려져 있습니다. 규칙을 고쳐도 데이터베이스 안의 내용은 바뀌지 않습니다.
- 이제 마스킹 규칙이 **패턴 자체에서 유도한 지문**을 가집니다. 사람이 기억해서 올려야 하는 상수는 결국 잊히고, 그 실패는 조용합니다.
- 이 지문은 색인기가 이미 비교하는 정책 지문에 합류합니다. 정책이 바뀌면 커밋이 그대로여도 ref를 다시 읽듯, **규칙이 바뀌면 다시 읽습니다.**

## 수정

### 라우트는 있는데 문서에 없는 엔드포인트가 있었습니다

- `GET /api/v1/admin/freshness`는 여러 릴리스 동안 운영자 화면에 데이터를 주면서도 `docs/openapi.yaml`에 없었습니다.
- 문서가 약속한 것이 서버에 있는지는 시험이 있었지만, **반대 방향은 없었습니다.** 콘솔만 아는 엔드포인트는 다른 누구도 쓸 수 없습니다.
- 문서에 추가하고, 반대 방향 시험을 넣었습니다.

## 검증

- 사내 설치에서 실제로 나오는 자격증명 10형태를 각각 확인 — 원문이 남지 않을 것, 조치에 필요한 호스트는 남을 것, 탐지 종류가 기록될 것
- **오탐 반대 시험**: 자격증명이 아닌 8형태(`https://host:7990/scm/...`, `git@host:org/repo.git`, `<property name="timeout" value="30"/>`, 산술식 등)가 그대로 통과하는지 확인
- 저장소 전체 354개 파일에 옛 규칙과 새 규칙을 각각 돌려 **차이만** 비교 — 새로 걸린 파일 없음, 기존 DSN 줄이 호스트를 보존하는 형태로 바뀐 것만 확인
- 규칙을 옛 형태로 되돌리면 정확히 URL 관련 4형태가 실패합니다
- 마스킹 지문이 호출마다 안정적이고, 규칙을 바꾸면 움직이는지 확인
- `GET /api/v1/admin/freshness`를 문서에서 빼면 새 시험이 실패합니다
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험, 릴리스 데이터베이스 업그레이드 시험, 콘솔 시험

## 업그레이드 참고

- **마이그레이션은 없지만, 첫 색인 주기에 모든 ref를 한 번 다시 읽습니다.** 마스킹 지문이 바뀌었기 때문이며, 이것이 새 규칙이 기존 내용에 적용되는 유일한 방법입니다. 커밋이 움직이지 않은 저장소도 포함됩니다.
- 재색인이 끝나기 전까지는 **저장된 청크에 옛 규칙의 결과가 남아 있습니다.** 소스 API에서 바로 오는 결과와 `read-file`은 읽는 시점에 마스킹하므로 즉시 새 규칙을 따릅니다.
- 대규모 설치에서는 첫 주기의 색인 부하가 평소보다 큽니다. 운영 화면의 색인 작업 큐에서 진행 상황을 볼 수 있습니다.

릴리스 자산은 아키텍처 접미사가 없는 다음 두 파일입니다.

```bash
sha256sum -c git-ctx-v0.75.0.tar.gz.sha256
gzip -dc git-ctx-v0.75.0.tar.gz | docker load
docker image inspect git-ctx:v0.75.0 --format '{{.Os}}/{{.Architecture}} {{.Config.User}}'
```
