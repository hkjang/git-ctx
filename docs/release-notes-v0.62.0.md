# git-ctx v0.62.0

이번 릴리스는 **같은 질문에 Bitbucket 과 GitLab 이 다른 답을 주던 것**을 없앱니다. 검색 플러그인 없는 Bitbucket Server 에서 코드 검색이 물러서지 않고 실패로 보고되던 문제가 핵심입니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### 검색 플러그인 없는 Bitbucket Server 에서 물러서지 않았습니다

- Bitbucket Server 는 검색 플러그인이 설치·활성화되어 있을 때만 인스턴스 전체 코드 검색에 답합니다. 없으면 그렇다고 말하는데, **말하는 방식이 배포마다 다릅니다** — API 가 501, 라우팅이 없으면 404, 앞단 프록시가 막으면 403, 이유를 담은 400.
- 이 중 **404 만 인식**하고 있었습니다. 나머지는 전부 "검색이 실패했다"로 caller 에게 전달됐고, 그래서 GitLab 이 줄곧 갖고 있던 **저장소별 대체 검색이 돌지 않았습니다**. 플랫폼이 느린 방법으로 답할 수 있었는데 에이전트는 검색이 깨졌다고 들었습니다.
- 두 클라이언트가 이제 같은 질문을 합니다. 500 은 그대로 실패입니다 — 기능이 없는 서버와 시도하다 깨진 서버는 다르고, 후자를 대체 경로로 감추면 진짜 장애가 느린 답 뒤에 숨습니다.

### 내용이 매치된 저장소가 목록에서 빠졌습니다

- `search-code` 의 저장소 목록에는 소스 자체의 검색 API 가 답했을 때만 그 저장소가 들어갔습니다.
- 같은 저장소, 같은 질의, 같은 파일이 매치돼도 — 검색 엔드포인트가 응답한 플랫폼에서는 이름이 나오고, 응답하지 않은 플랫폼에서는 빠졌습니다. **답이 인덱스에서 온 경우도 마찬가지**였는데, 위키 페이지와 이슈는 항상 그 경우입니다.
- 이제 내용이 매치된 저장소는 누가 찾았든 목록에 들어갑니다. 히트는 이미 ACL 을 통과했으므로 저장소 이름을 말하는 것이 새로 드러내는 정보는 없습니다.

## 검증

- **플랫폼 차분 시험**을 새로 추가했습니다(`TestBothPlatformsAnswerTheSameToolsIntegration`). 같은 파일들을 Bitbucket 과 GitLab 양쪽에 색인하고, 읽기 도구 21개를 같은 인자로 부르고, 식별자(라이브러리 ID·프로젝트 키·커밋·URL)만 접은 뒤 **답이 같기를** 요구합니다.
- 비교가 의미를 가지려면 두 픽스처가 실제로 동등해야 하므로, 가짜 서버들도 같은 이름·설명·커밋을 내놓고 같은 방식으로 검색 부재를 알리도록 맞췄습니다. Bitbucket 가짜는 이제 `name=` 필터를 실제 API 처럼 존중합니다 — 그러지 않으면 이 플랫폼이 매치하지 않는 이름도 매치하는 것처럼 보입니다.
- Bitbucket 거절 4가지(501·404·403·400)가 각각 대체 경로를 타는지, 500 은 타지 않는지 단위 시험. 수정을 되돌리면 4개 중 3개가 실패합니다.
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- `search-code` 의 저장소 목록이 이전보다 길어질 수 있습니다. 내용이 매치된 저장소가 추가된 것이며, 히트 순서를 따릅니다.
