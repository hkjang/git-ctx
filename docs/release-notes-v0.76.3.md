# git-ctx v0.76.3

이번 릴리스는 **등록된 경로에 저장소가 없을 때, 그것이 무엇을 뜻하는지 말하지 않던 문제**를 고칩니다. 기본 서비스 포트는 계속 `4747`이며 기존 API·MCP 호환성을 유지합니다.

## 수정

### 소스가 보낸 "존재하지 않는다"를 사실인 것처럼 그대로 전달했습니다

- 저장소가 등록된 경로에 없으면 색인이 이렇게 실패했습니다:

  ```
  list branches for KCB/old-name: bitbucket API 404 Not Found:
  {"errors":[{"message":"Repository KCB/old-name does not exist."}]}
  ```

- 그런데 그 문장은 **사실이 아닙니다.** Bitbucket과 GitLab은 **서비스 계정이 볼 수 없는 저장소에도 403이 아니라 404**를 돌려줍니다. 권한 없는 호출자가 "없음"과 "거부"를 구분하지 못하게 하려는 의도적인 설계입니다. 그리고 그 문장을 읽는 운영자도 구분할 수 없습니다.
- 가능성은 셋이고 **조치가 각각 다릅니다** — 이름이 바뀌었거나, 삭제됐거나, 서비스 계정의 권한이 회수됐거나. 기존 메시지는 어느 쪽도 뒷받침하지 못했습니다.

### 플랫폼만 아는 사실이 하나 더 있었습니다

- 저장소 항목은 **경로가 아니라 소스 ID로 식별**됩니다. 그래서 현재 이름으로 **다시 등록하면 새 항목이 생기지 않고 기존 항목이 갱신됩니다.**
- 이름이 바뀐 뒤 운영자가 원하는 동작이 바로 그것인데, **아무것도 그렇게 말하지 않았습니다.** 이제 메시지에 그 ID와 함께 나옵니다.

### 잘려도 쓸모 있도록 순서를 정했습니다

- 콘솔은 실패 메시지를 **300자로 자릅니다.**
- 그래서 설명을 원본 오류 **앞에** 두고, ID를 그 설명의 **앞쪽에** 두었습니다. 잘림에서 살아남는 부분이 "무엇을, 어떻게 해야 하는가"여야 하기 때문입니다.
- 소스가 보낸 원문은 **버리지 않고** 쓸모 있는 부분 뒤에 그대로 둡니다.

### 404만, 그것도 이 호출에서만

- 저장된 project·slug를 쓰는 **첫 번째 호출**이므로, 여기서의 404는 파일이나 ref가 아니라 저장소에 대한 것입니다.
- **깨진 서버를 옮겨간 저장소로 포장하지 않습니다.** 500은 500으로 남습니다.

## 검증

- 404를 돌려주는 소스로 실제 색인 작업을 돌려, 세 가지 가능성·`404, not 403`·소스 ID·재등록 안내가 모두 들어가는지 확인
- **300자 안에** ID와 재등록 안내가 들어가는지 확인 — 잘려도 조치가 남아야 합니다
- 소스 원문이 유지되는지 확인
- 500을 돌려주는 소스로 돌려, 옮겨간 저장소로 보고되지 않고 500이 남는지 확인
- 수정을 되돌리면 시험이 실패합니다
- FTS5 빌드·태그 없는 빌드·PostgreSQL 3가지 조합 전체 단위·통합·race 테스트, 빌드 모드 교차 시험, 릴리스 데이터베이스 업그레이드 시험, 콘솔 시험

## 업그레이드 참고

- 마이그레이션이나 재색인은 필요하지 않습니다.
- 색인 실패 메시지의 문구만 바뀝니다. 재시도 횟수와 백오프는 그대로입니다.
- 이름이 바뀐 저장소는 **현재 이름으로 다시 등록**하면 됩니다. 소스 ID가 같으므로 청크·심볼·권한이 그대로 유지되고, 항목이 두 개로 늘지 않습니다.
